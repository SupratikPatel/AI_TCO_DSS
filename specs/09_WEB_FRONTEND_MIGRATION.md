# Web frontend migration — approved direction

Decision date: 2026-11-07. The author rejected the Streamlit approximation of the
Stitch design and explicitly requested a dedicated web UI, accepting the additional
implementation work. This document supersedes the Streamlit delivery instructions
in the original MVP documents. Requirements 1–42 retain their domain meaning except
for the delivery-specific replacements below; Requirement 43 defines the migration.

## Target architecture

- `frontend/`: React + TypeScript, Vite, Tailwind CSS, shadcn/ui primitives styled to
  the actual Stitch design. Default library styling is not the visual target.
- `src/ai_tco_dss/api/`: FastAPI adapter with typed Pydantic requests/responses.
- Existing `services/`, `domain/`, `catalog/`, `engines/`, and future `decision/`
  remain the computation boundary. No financial, sizing or ranking math in JavaScript.
- Plotly.js renders interactive memory and timeline charts from typed service
  results. Python Plotly figures are reference implementations, not the API format.
- Generate TypeScript API types from OpenAPI and check for drift. Start with a small
  typed fetch client; add state libraries only if the implemented workflow needs them.
- Python dependencies remain managed by uv; frontend dependencies use npm with a
  committed lockfile. Pin compatible versions during implementation, not in this plan.

Task 8 now implements `frontend/`, the FastAPI adapter and the verified root
`npm run dev` launcher. Windows `run.bat` starts the web UI/API and opens the browser;
`run.sh` retains the legacy prototype until Task 13. See `design/stitch/REVIEW.md` for browser evidence and
the README for working commands and remaining scope.

## API boundary

Versioned endpoints (size/TCO foundation implemented in Task 8):

| Route | Purpose | Existing service / contract |
|---|---|---|
| GET /api/v1/health | Process readiness | Small health response |
| GET /api/v1/catalog | Selectable IDs, labels, counts and FX metadata | catalog_overview / CatalogOverview |
| GET /api/v1/workloads/default | Initial workload | load_workload / WorkloadProfile |
| POST /api/v1/size | One hardware/model pairing | size / SizeRequest → SizeResult |
| POST /api/v1/tco | Selected on-premise anchor and comparisons | project_tco / TcoRequest → TcoProjection |
| POST /api/v1/recommend | Ranked and rejected candidates | recommend / RecommendRequest → Recommendation (Task 9) |
| POST /api/v1/evaluate | Complete scenario result | evaluate_scenario / ScenarioRequest → ScenarioResult (Task 9) |

Task 8 also supplies `GET /api/v1/scenario/default`, `POST /api/v1/scenario/validate`
and `GET /api/v1/options` to keep domain defaults, validation and selectable
open-model/node-count metadata in Python. The recommend/evaluate routes remain
absent until their services exist. OpenAPI types are generated by
`scripts/api-types.mjs` and checked by `npm run types:check`.

Verify the actual contract names before generating the client. Map validation,
unknown identifiers, configuration failures and unexpected errors to documented
HTTP responses; do not return partial success or stack traces as user messages.
Do not expose recommendation routes backed by fabricated results before Task 9.
Keep API calls stateless; isolate each browser's inputs and selected candidates.
Use a Vite development proxy; define a same-origin production serving strategy in
Task 13. CORS must use explicit local origins if separate origins are required.

## Reuse and retirement

Preserve the Task 1–7 domain work and the Task 8 rental/hybrid/timeline functions,
service orchestration and numeric tests. Their implementation does not establish
empirical accuracy; existing ledger limitations still apply.

`src/ai_tco_dss/ui/`, `.streamlit/config.toml`, AppTest checks and fragment-specific
tests describe the legacy prototype. Freeze visual work there. Keep them during
the transition for comparison; remove Streamlit code, dependency, config and
launcher integration at the Task 13 cutover after React equivalents pass. Separate
mixed calculation/AppTest tests before retiring the latter. Never remove numeric
regressions just because their test file also contains UI checks.

The rejected Task 8 screen is not an accepted frontend deliverable. Its historical
test results remain useful evidence about the prototype, not web UI validation.

## Visual implementation contract

Use `specs/08_MVP_DESIGN_REFERENCE.md` for exact Stitch resource IDs. Export the
selected HTML, screenshots and design-system text into `design/stitch/` with a
manifest of source screen, retrieval date, viewport and chosen canonical variant.
Keep those exports as references. Implement proper React components and local CSS
tokens; do not embed the generated page in an iframe or reproduce Streamlit chrome.

Build the desktop shell first: fixed-width scenario sidebar, compact project
header, five aligned KPI cards, tab strip, analytical panels and audit/export.
Use the light TCO screen as the first canonical layout and its dark counterpart
for dark mode. Use the ranking and memory screens for their tab-specific content.
Preserve the reference's proportions, typography, spacing, borders, density,
icons, selected states and chart/table placement. Adjust clipped names and weak
contrast rather than copying defects. Use real catalog labels and units.

Functional differences from generated examples: Normal mode uses SAW and only the
approved scenario inputs; Expert mode exposes weights/TOPSIS. Five KPI meanings
stay consistent between tabs. No hardcoded results, NPV/WACC switch, P95 claim,
certification badge or cryptographic verification unless actually implemented and
separately specified. Preview fixtures may populate isolated development/test
screens, clearly identified as fixtures; they must not appear as live calculations.

Use one source of scenario state, retain the last valid inputs on validation
errors, cancel/ignore stale API responses, and distinguish loading, no feasible
option, missing benchmark data, catalog errors and server errors. Independent
simulator inputs must not reset or recompute unrelated panels. Changing ranking
weights cannot remedy a hard-filter failure. No featureless clickable controls.

## Acceptance and verification

1. Compare browser screenshots side by side with exported Stitch screens at the
   reference logical desktop width (1280 CSS px); also check 1440 desktop and
   768/390 CSS px responsive layouts. Normalize DPR when comparing 2560px exports.
2. Verify light and dark modes, full candidate names, readable tables/legends,
   keyboard focus, labelled inputs, badges that do not rely on colour alone, and
   no page-level horizontal overflow. Dense tables may scroll within their panel.
3. Automate component/interaction tests with Vitest + React Testing Library and
   real-browser flows/screenshots with Playwright. Establish a reviewed screenshot
   baseline from the implemented reference match; passing logic tests alone does
   not satisfy visual acceptance. If browser access fails, leave visual acceptance
   pending and report the blocker explicitly.
4. Test API/service parity, deterministic outputs, errors, monetary USD payloads,
   display-only EUR conversion and generated-type drift. Keep offline Python tests.
5. Preserve the existing calibration expected failures and identify the unrelated
   missing thesis-document tests separately. Do not weaken tests to hide failures.
6. Task 13 must provide one documented verification entry point that runs Python,
   API, frontend type/lint/build/tests and browser checks; before then report each
   command independently. `scripts/verify.py` currently verifies Python only.
